## Concrete challenges and required wording

1. **Do not present the multiplier as a diagnosed scheduler root cause.** In `../access_policy/review/spaces_0_50_2_source/spaces/zero/client.py:124–146`, the non-`xlarge` path multiplies declared duration by hardware `duration_factor` for scheduling but displays the original duration. `configs.json` gives Blackwell 1.5 and default H200 1.0; `config.py` selects based on remote driver data, falling back to the default. Under Blackwell/non-`xlarge`, 120 becomes 180, exceeding 176. No saved evidence establishes the actual selected remote configuration or scheduler comparison rule. The saved arithmetic explicitly shows that 180 is not less than 180. Therefore: “a source-supported conditional explanation for 176,” not “quota discrepancy solved,” “all quota errors explained,” or “authentication will fix it.” Metadata matching package version is useful provenance, not a hash of the live server's imported files.

2. **The post-restart 401 does not isolate the user's secret.** `../access_after_restart.json` records an injected variable present, default token resolution, official `HfApi.whoami`, HTTP 401 and no returned identity at 10:18:05 UTC. This establishes failure of that effective authentication request. It cannot distinguish invalid/revoked token contents from proxy replacement, binding propagation, destination handling or account-specific restrictions. Do not ask for a replacement secret as a proven remedy, claim the user entered it incorrectly, or equate environment-variable presence with authentication. A future meaningful auth-path change justifies one read-only identity retry; successful identity still would not guarantee either generation or export admission. No such new retry was performed by this review.

3. **fal is an executable design candidate, not an execution-ready or exact-reproduction result.** `../commercial_routes/review/fal_schema.json` exposes the 16 inherited numeric controls. `../fal_request_preparation.json` and `../../source/prepare_fal_request.py` establish offline validation, exact original-image roundtrip and explicit defaults for additional controls; they do not establish accepted service input or successful execution. fal exposes no checkpoint revision, `1024_cascade` selector, preprocessing bypass or separate processed-image/preview-before-export gate. Same seed and setting names do not close these gaps. The endpoint's decimation target is documented as vertices; do not convert it into guaranteed triangle count. Call this “documented same-family alternative with changed provenance/checkpoints,” not “same pipeline” or “equivalent reproduction.” Even the inherited official Space plan did not prove its actual loaded checkpoint revision.

4. **The advertised $0.30 is not the complete enabling cost.** At 1024, the public model page's advertised per-request price is $0.30. There is no authenticated balance, invoice, purchase minimum or successful charged call. A valid FAL_KEY, sufficient spendable prepaid balance and acceptance of the provider/input/provenance change are missing. The inherited execution contract is explicitly free-only/no-paid. Preparing the local payload does not amend it; it contains the real original image as a data URI but was not uploaded. Any final action request should be for the concrete one-candidate paid route and a spend ceiling, with unknown minimum top-up disclosed. Do not imply that entering a key alone supplies funding or that a $0.30 top-up is available.

5. **One public GLB is stronger than a format promise but much weaker than full material fidelity.** The linked sample receipt and inventory agree on SHA-256 `a8b528d7715ada8dfa5c7dd0ac63abe47c682752db86bfbf4625f516cc443b2a`. It is a public endpoint documentation example, not an output for the user's input or known generation settings. The inventory records one primitive, UV0, normals, one material, embedded base-color and metallic/roughness textures, and required `EXT_texture_webp`. It has `alphaMode: OPAQUE`, no `normalTexture`, no animation, and no evidence of door components or transparent vehicle glass. “Contains UV and metallic-roughness PBR data” is justified; “all PBR channels preserved,” “DCC compatible generally,” “glass-ready,” or “door-editable” is not. A single provider-linked example does not guarantee these channels for every output or prove current model provenance.

6. **The validator failure must remain visible without becoming an asset-rejection shortcut.** `../public_fal_sample/gltf_validation.json` reports 18 `ACCESSOR_VECTOR3_NON_UNIT` errors, four buffer-target hints, zero warnings, and `truncated: false`. The normals have near-zero reported lengths. These are concrete glTF conformance errors, not merely warnings; conversely, a loader might import the file successfully. An import-only Blender check can resolve whether this exact artifact loads in that recorded version and whether its UV/material/image data are represented. It cannot establish untouched normal preservation, identical rendered appearance, round-trip export fidelity, general DCC compatibility or successful car authoring. If a loader normalizes or substitutes data internally, import success does not make the preserved raw GLB validator-clean. No repair is warranted within this review.

7. **Update stale scope statements rather than flattening all evidence into “untested.”** `../commercial_routes/review/INDEPENDENT_REVIEW.md` says “No ... GLB content ... was tested.” That remains accurate for that review's scope and the user's car, but is stale as an overall-task conclusion after the public-example inventory and validator check. Report the public sample as a separate format probe. Similarly, “no further useful work exists” is broader than the evidence: the parent's bounded sample import check is useful independent work. The defensible stopping point is that an actual user's-car acquisition is blocked under the present authorized routes/prerequisites, after independent bounded evidence checks, not that TRELLIS.2 or image-to-3D is impossible.
